# 13 场景贯穿：把活动报名与会员管理应用做出来

一位创业者希望经营活动社群，需要一款应用把活动展示、会员报名和签到名单放在一起。他的目标是让会员能够顺利找到活动并完成报名，让自己能够维护活动和会员关系。以下场景将 OPC 的产品能力连成一轮完整工作，展示目标如何成为产物，产物如何成为版本，版本如何进入持续经营。场景为能力示意，涉及的界面、任务和反馈不代表真实用户数据。

## 把想法说成能够执行的目标

创业者在个人云中说明希望服务的对象、报名流程与当前最重要的交付结果。他提出会员报名、活动管理和导出签到名单等需求，同时与机组明确本轮应先做到什么。需求工作将业务目标与验收要求保留在项目中，使后续设计、开发和检查能够围绕同一方向展开。

这一阶段的判断会影响整个交付。如果最重要的是让第一场活动顺利报名，工作应围绕会员发现活动、进入报名流程和管理者使用名单展开。范围越清楚，各项任务越容易知道自己的结果将交给谁。创业者仍然可以调整目标，项目中的需求和产物则让调整有依据，也让智能体能够继续处理变化。

## 让能够独立推进的工作同时展开

在共同需求下，界面方案、报名页面、会员功能和检查工作按依赖关系组织。可以独立推进的部分同时进行，各自更改保留在独立工作树中；需要前一项结果的部分，在相关产物形成后继续。机组分工服务于实际任务，不要求每次沿固定角色或数量展开。

设计产物帮助创业者判断页面是否清楚，功能产物说明报名与会员如何衔接，测试结果帮助检查本轮用户流程。每项工作都在共享项目中留下结果，交接因此能够从“已经处理”进一步变成“这里是可以查看的产物”。创业者可以提出具体修改，例如让会员入口更突出，或让活动说明更准确，再由智能体沿相应任务继续执行。

## 整合成一版完整应用

报名工作树与会员工作树的更改回到同一项目中整合。用户在完整版本中检查入口、报名与名单相关体验，判断是否达到本轮需求。单项完成与整体可用之间，由整合和检查衔接；审阅中发现的问题继续回到任务处理，版本保留修改结果。

应用经确认后默认发布到个人云。创业者拥有了可以进入经营的版本，也保留了执行环境、项目文件与更改记录。机组继续准备版本说明、文案与海报，用户检查对外表达是否与实际功能一致，确认后发布到相应社交平台。应用上线与用户沟通因此沿同一项目衔接。

## 让业务回应进入下一版

应用发布后，业务群中的会员提出“希望更快找到专属报名入口”。OPC 工作台通过 API 读取获授权的群聊业务背景，将这条反馈带入现有项目。已有页面、会员流程和上轮产物为理解反馈提供背景，创业者据此明确本轮重点：让会员入口更容易发现，并保持报名流程衔接。

界面调整与相关功能更改继续在独立工作树中推进，再整合、检查并形成新版本发布。创业者可以在手机上查看进展和提出意见，回到电脑后继续审阅同一项目。新的文案与海报围绕本轮实际变化准备，经确认后对外发布。下一次反馈仍然能够回到原项目，经营中的小改进逐渐积累成更适合业务的应用。

## 在需要时引入创作者与复用能力

如果创业者希望进一步改善活动页面，可以在应用市场发布明确工作，选择具有相应作品的创作者。创作者接受任务后使用智能体推进，提交界面或功能产物，创业者审阅并确认交付。市场记录进度与评价，个人云保留项目中的具体结果，下一轮工作仍可沿版本继续。

成熟的应用、智能体或模板也可以成为市场供给，为其他活动经营者提供起点。不同业务的会员规则与页面要求有所差异，新使用者仍需结合自身目标选择与调整。复用帮助工作更快开始，清楚的业务背景和验收则帮助结果适合本次经营。

整个场景中的模型调用、工具使用、智能体执行与市场服务交易，通过 SIGN 接入底层结算。用户从自己的工作需要出发购买服务，机组围绕项目交付，创作者围绕委托提供能力。个人云让这些活动共同指向一款持续成长的应用，也让一个人的业务能够获得更完整的执行支持。
